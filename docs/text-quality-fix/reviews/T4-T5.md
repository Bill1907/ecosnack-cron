## 3. 코드 검토

### 3.1 Prisma 7.2 `createMany` + `skipDuplicates` (로컬 근거)

- **타입.** `node_modules/.prisma/client/index.d.ts:1930`: `createMany(...)` 의 반환형은 `PrismaPromise<BatchPayload>`(`{count}`)다. `:2484-2490`: `ArticleCreateManyArgs = { data: ArticleCreateManyInput | ArticleCreateManyInput[]; skipDuplicates?: boolean }`.
- **JSON null.** `index.d.ts:9286-9291` 에서 `ArticleCreateManyInput` 의 `soWhat/impactAnalysis/relatedContext/sentiment` 는 `NullableJsonNullValueInput | InputJsonValue` 이고, `:8510-8515` 에 따르면 `NullableJsonNullValueInput` 은 `DbNull | JsonNull` 이다. 따라서 `toJsonValue` (`src/services/database.ts:50-57`)가 돌려주는 `Prisma.DbNull` 은 createMany에서도 유효하다. typecheck도 통과했다. 가짜 어댑터로 넘어간 인자를 보면 `DbNull` 은 SQL `null` 로, 값은 `"{\"a\":1}"` 문자열로 바인딩됐다. `JsonNull`(JSON 리터럴 `null`)이 섞이지 않았다.
- **SQL.** 3행을 넣었을 때 실제로 생성된 문장은 아래 하나다(`probe-prisma.ts`).
  `INSERT INTO "public"."articles" ("title","link",…,"is_exemplar","created_at") VALUES ($1…$17), ($18…$34), ($35…$51) ON CONFLICT DO NOTHING`
  충돌 대상 없는 `ON CONFLICT DO NOTHING` 이다. 지금 unique 제약은 `link` 와 PK `id` 뿐이라 `update: {}` upsert와 의미가 같다.
- **count.** 런타임에서 `affectedRows` 매핑은 `{count: e}` 다(`node_modules/@prisma/client/runtime/client.js:11`, minified offset ≈82825 `case"affectedRows"`). 어댑터가 영향 행 수 2를 돌려주게 하면 결과는 `{"count":2}` 다. 5000행을 넣으면 INSERT 3개로 나뉘고 count는 각 영향 행 수의 합(6)이다. `ON CONFLICT DO NOTHING` 의 영향 행 수는 실제로 들어간 행 수이므로 count는 신규 삽입 수다.
- **내부 트랜잭션과 5초 한도.** 행이 3개뿐이어도 Prisma 7.2는 createMany를 내부 트랜잭션으로 감싼다(`startTransaction → INSERT → COMMIT` 이 관측됨). 커밋 제목의 "트랜잭션 없는"은 엄밀하지 않다. 다만 이 트랜잭션에는 시간 한도가 없다.
  - `client.js:11` (offset ≈108073): 쿼리 플랜의 `case"transaction"` 은 `startInternalTransaction()` 을 부른다.
  - 같은 줄 offset ≈113714: `startInternalTransaction(t){let r=t!==void 0?this.#s(t):{}` 이므로 옵션은 `{}`, 즉 `timeout`·`maxWait` 가 undefined 다.
  - offset ≈117770: `function ga(e,t){return t!==void 0?setTimeout(e,t):void 0}` 이므로 timeout이 undefined면 타이머를 걸지 않는다(`#l` 의 만료 타이머도 `ga` 를 쓴다).
  - 반대로 예전 `$transaction([...])` 은 `client.js:58` (offset ≈135646) `requestBatch` 의 `case"multi"` 에서 `this.transaction("start",{},this.config.transactionOptions)` 를 부르고, `client.js:70` (offset ≈157614)의 기본값 `timeout ?? 5e3`, `maxWait ?? 2e3` 이 적용된다.
  - 지연 실측(`probe-timeout.ts`, 가짜 어댑터에 쿼리당 지연을 넣음):
    - 예전 경로, upsert 20개, 쿼리당 100ms: 5246ms 뒤 `The timeout for this transaction was 5000 ms, however 5169 ms passed` 로 실패. 쿼리 54개가 순차로 나갔다. 운영 로그(5,0xx~5,5xx ms 초과)와 같은 양상이다.
    - 새 경로, 20행, INSERT 한 번에 6000ms 지연: `OK in 6046ms`, 문장은 `BEGIN/INSERT/COMMIT` 뿐이다.
  - `@prisma/adapter-neon` `dist/index.js:617-648` 의 `startTransaction` 은 Pool 연결 + `BEGIN`(격리수준을 지정하면 `SET TRANSACTION`)뿐이고 자체 타이머가 없다.
  - 결론: 같은 5초 한도에 다시 걸릴 경로는 없다. 왕복은 20회 이상에서 3회(BEGIN·INSERT·COMMIT)로 준다.

## 권고 (차단 아님)

1. **주석·커밋 문구.** `database.ts:164·175` 와 커밋 제목은 "트랜잭션 없는 단일 INSERT"라고 하지만, Prisma 7.2는 BEGIN/INSERT/COMMIT으로 감싼다. 다만 타임아웃 없는 내부 트랜잭션이다. 다음에 손댈 때 주석을 "시간 한도 없는 내부 트랜잭션 안의 INSERT 한 번"으로 고치면 오해가 없다.
2. **단위 테스트는 count의 의미를 보지 않는다.** `getPrisma` 를 목으로 바꾸기 때문에 `ON CONFLICT DO NOTHING` SQL과 count=영향 행 수는 단위 테스트로 고정되지 않는다. H6(Neon 브랜치에서 신규·중복 섞어 20건)을 생략하지 말 것. 원하면 이번 `probe-prisma.ts` 같은 가짜 driver adapter 테스트(네트워크 없음)로 생성 SQL에 `ON CONFLICT DO NOTHING` 이 있고 count가 영향 행 수와 같다는 점을 고정할 수 있다.
3. **충돌 대상 없는 `ON CONFLICT DO NOTHING`.** 나중에 `articles` 에 unique 제약이 더 생기면 그 위반도 조용히 "중복"으로 처리된다. 지금은 문제가 없다.
4. CBS 피드의 `/video/` 링크 항목(픽스처 8개 중 2개)은 지시대로 거르지 않았다. 운영에서 비중을 관찰할 것.

## 같은 종류 탐색

- **다른 `$transaction` 사용처: 없음.** `src/`, `tests/`, 루트 `*.ts` 를 grep하면 `$transaction` 은 이번에 지운 주석 한 줄(`database.ts:175`)과 테스트 목뿐이다. `transactionOptions` 를 지정한 곳도 없다.
- **리포트 저장 `dailyReport.upsert` (`src/services/daily-report.ts:507`): 5초 위험 없음.** 가짜 어댑터(쿼리당 3000ms 지연)로 돌리면 트랜잭션 없이 `INSERT … ON CONFLICT … DO UPDATE` 문장 하나로 컴파일되고 `OK in 3045ms` 였다(`probe-report.ts`). 개별 저장 폴백의 `findUnique` / `create` 도 각각 단일 문장이고 트랜잭션이 없다.
- **폴백이 실패를 가린다(P5와 같은 구조가 남아 있음).** 일괄 저장이 실패해도 개별 저장이 성공하면 작업은 `ok:true` 로 끝나고, 남는 것은 `배치 저장 실패` error 로그 한 줄이다(`database.ts:202-207`). 28회 연속 실패가 대시보드에 드러나지 않았던 이유가 이것이다. createMany가 다른 이유로(예: Workers에서 Pool 연결 실패) 매번 실패해도 똑같이 조용하다. `CollectNewsResult` 에 `batchFallback: true` 같은 표시를 두거나 경고 집계를 권한다.
- **피드가 죽어도 아무도 모른다(Yahoo가 17일간 죽어 있던 원인 그대로).** `news-fetcher.ts:179-182` 는 실패를 `[] + error 로그` 로 삼키고, `fetchAllNews` (`:201-216`)는 항상 `success:true` 를 돌려준다. 여섯 피드가 전부 죽어도 `collect-news.ts:39-40` 에서 warn 한 줄만 남기고 `ok:true` 이고, `worker.ts:36` 에서 throw되지 않는다. 새 CBS 피드도 똑같이 조용히 죽을 수 있다. PLAN §8에서 "피드 실패 알림"으로 미뤄 둔 항목이다. 최소한 "소스별 0건 / 전체 0건이면 `ok:false`" 정도를 권한다. 이번 커밋의 결함은 아니다.
