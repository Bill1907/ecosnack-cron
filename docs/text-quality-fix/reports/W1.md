### 판단한 것과 이유
1. **`inSource` 필드는 `labels.json` 에 없다.** 지시문은 "`inSource`를 옮긴다"고 하지만 원본 124개 항목의 키는 `sid, kind, id, path, run, context, set, label, confidence, reason, fix, detector_expected` 뿐이다. 이의를 달고 멈출 만큼 모호하진 않다고 보고(의도가 분명: "입력 원문에 있는 한자"), 픽스처를 만들 때 `label==="normal" && reason.includes("원문")` 으로 파생해 명시적 `inSource` 불리언으로 넣었다. 결과 40개 = 표본(set=sample) 40개 전부. 처음엔 `label` 조건 없이 `reason.includes("원문")` 만 썼는데 오염 3건(S0113·S0619·S0689: reason 의 "원문 확인 필요")이 잘못 true 가 돼서 정상 라벨로 한정했다. **파생 기준은 사람이 확인해 주길 바란다.**
2. **지시문 누출 패턴은 초안 그대로 보정 없이 통과**: expected=true 67/67 검출, expected=false 70/70 0건. 한 줄도 고치지 않았다(과적합 방지 차원에서 일부러 안 건드림).
3. **라벨 정답 사용**: 테스트는 `detector_expected` 를 기대값으로 쓰고 구현을 호출해 기대값을 만들지 않는다. 정상 라벨(77개 중 detector_expected=false)은 `findForeignScript` 결과가 **빈 배열**(지시문 누출 포함)이어야 통과로 센다. 오염 라벨은 foreign-script 가 1건 이상이면 통과이고, 추가로 "라벨된 `run` 을 포함하는 덩어리로 잡히는지"를 따로 확인한다.
4. **`ScriptIssue.reason` 타입**: 지시문은 `string` 이지만 `"foreign-script" | "prompt-leak"` 유니온으로 좁혔다(`string` 에 대입 가능, 호출부 영향 없음).
5. **`describeScriptIssues(issues)` 추가(지시문에 없는 공개 함수)**: T2·T3 가 똑같이 "문제 목록 → `언어 오염: <사유>` 의 사유 문자열"이 필요한데 같은 코드를 두 군데 쓰지 않으려고 T1 에 두고 테스트도 붙였다. 앞 5건만 `path "run" (reason)` 형식으로 적고 나머지는 `외 N건`, run 은 30자에서 자른다(로그 폭주 방지). 불필요하다고 판단되면 이 함수만 떼어도 나머지는 영향 없다.
6. **덩어리 규칙**: 정상 문자 클래스(Hangul, Latin, Greek, Common, Inherited)의 여집합 한 글자 + 이어지는 (여집합 | `\p{M}`) 를 한 덩어리로 뽑는다. `\p{M}` 을 "여집합 글자 뒤"에만 허용해서 라틴 글자에 붙은 악센트(`Café`)는 덩어리가 되지 않는다. 덩어리가 한자(Script=Han)로만 이뤄졌을 때만 ①②③ 예외 판정, 가나·한자가 섞이거나 가나/아랍/키릴만 있으면 입력 원문에 있어도 무조건 오염.
7. **②는 직전 두 글자만 본다**: `text[index-1]==="("`, `text[index+len]===")"`, `text[index-2]` 가 한글. 공백이 끼면(`다산 (多産多死)`) 오염, 전각 괄호도 오염으로 본다(재생성되는 쪽이 안전).
8. `source` 기본값 `""`(`findForeignScript(text, source = "")`). `source.includes("")` 가 true 가 되지 않도록 한자 덩어리는 항상 1글자 이상이라 문제 없음(빈 덩어리 없음).

### 의심스러운 것
- **입력 원문에 있어도 가나·아랍·키릴은 오염**(지시 그대로). (가정 예시) 입력 기사에 `Яндекс`, `ヤフー` 같은 표기가 있고 모델이 그대로 옮기면 3번 모두 오염 판정 → 그 기사는 Stage 3 실패로 스킵된다. 한자는 ①로 구제되지만 가나·키릴·아랍은 안 된다. 실제 입력 피드에서 얼마나 나오는지는 측정하지 않았다. H4 dry-run 에서 `언어 오염` 재시도 건수를 보고 판단해야 한다.
- **`\d+\s*자\s*(이상|이내|이하|내외|분량)`** 은 정상 기사에도 걸릴 수 있다("비밀번호 12자 이상", "10자 이내"). 70개 정상 요약에는 0건이지만 표본이 한국 경제 기사 요약뿐이다.

- **Script=Unknown(미할당 코드포인트, 사설 영역, 짝 없는 서로게이트)** 도 "그 밖의 문자"라 오염으로 잡힌다. 의도한 동작이지만 지시문에 명시된 건 아니다.
- 신문 약어 허용 목록 38자는 지시문 그대로다. `李文尹`(이름), `文`, `新舊`, `前後` 는 라벨 코퍼스에서는 `李` 한 글자만 근거가 있고 나머지는 지시문의 오케스트레이터 확정 목록이다.

### 판단한 것과 이유
1. **오염 로그를 `createStructured` 안에서 남긴다.** 테스트가 "1회차 오염 → 2회차 정상 성공" 에서도 로그에 `언어 오염` 이 있어야 한다고 요구한다. `withRetry` 의 기본 로그("재시도 1/2 …")에는 사유가 없으므로, validate 위반 시점에 시도마다 한 줄 남긴다. T3 도 같은 코드를 타서 공짜로 얻는다. 시도마다 한 줄이라 H4 dry-run 에서 `grep -c "언어 오염 감지"` 로 재시도 건수를 센다. 최종 실패 시에는 analyzer 의 기존 `상세 분석 오류` 로그에 같은 사유가 한 번 더 나온다(중복 1줄, 의도).
2. 사유 문자열은 T1 의 `describeScriptIssues` 형식: `so_what.main_point "深" (foreign-script)`. 테스트가 `keywords[1] "次の"` 형식을 기대해서 그대로 맞았다.
3. `validate` 의 인자 타입을 `z.infer<S>` 로 해서 호출부에서 `out` 이 스키마 타입으로 추론된다. 기존 호출부(article-scoring, evidence-validator)는 `validate` 를 안 쓰므로 동작·재시도 횟수·400 계열 비재시도 처리 그대로(테스트로 고정: `validate 가 없으면 이전과 같다`, `비재시도 HTTP 오류(400)는 … 한 번만`).

### 의심스러운 것
- **재시도가 기사별 타임아웃 하나를 공유한다.** `createStructured` 의 `timeoutMs: 170_000` 이 `withRetry` 전체를 감싸고, 바깥 `PER_ARTICLE_TIMEOUT` 은 180초다. 오염 재시도가 늘면 3회째 전에 타임아웃으로 끊길 수 있다(그 경우 기존대로 실패로 센다). 기사 한 건 생성 시간이 얼마인지 측정하지 못했다. H4 에서 `타임아웃` 로그를 같이 봐야 한다.

### 판단한 것과 이유
1. **"입력에 있는 한자는 통과" 테스트는 `電子` 로 쓴다.** 지시문 예시 `美 10년물` 의 `美` 는 신문 약어 허용 목록에 있어서 입력에 없어도 통과한다. 입력 원문 규칙(①)을 실제로 검증하려면 목록에 없는 글자(`電子`)가 필요하다. 반대편은 "입력에 없으면 `電子` 재시도, `美` 는 통과" 테스트로 고정.
2. **sanitize 전 검사 테스트는 sanitize 가 실제로 지우는 문구로 쓴다.** `600자 이상으로 작성했어요` 는 `sanitizeMetaComments` 의 첫 패턴에 걸려 지워지고, 지시문 누출 패턴(`\d+\s*자\s*(이상|…)`)에도 걸린다. 검사가 sanitize 뒤였다면 재시도가 없었을 것이므로(호출 1회) 순서를 구분하는 테스트가 된다.
3. 목: `getPrisma` 와 `chat.completions.create` 만 바꾸고 `skipQualityEvaluation: true` 로 Jev 호출을 피했다.

### 의심스러운 것
- **sanitize 전 검사의 부작용.** `sanitizeMetaComments` 가 조용히 지워 주던 "N자 이상으로 작성" 류가 이제는 재생성(최대 3회 호출, 유료) 사유가 된다. 지시대로 했지만, 리포트는 호출 한 번이 비싸므로(max 32000 토큰) 이 문구가 얼마나 자주 나오는지 H4 에서 `언어 오염 감지 - … prompt-leak` 건수를 봐야 한다.
- **과거 기사 오염이 리포트 입력으로 들어간다.** `formatArticlesForAI` 는 DB 의 `headlineSummary`·`soWhat` 등 생성 텍스트를 프롬프트에 넣는다. 운영 DB 에 오염된 행이 있다면(스캔에서 47건 확인) 리포트 모델이 그 한자를 그대로 옮길 수 있고, `source`(제목+설명만)에는 없으므로 3회 모두 실패할 수 있다. 특히 과거 날짜 백필(`--from --to`)에서 위험. T2 배포 후 새로 쌓이는 기사는 깨끗하지만 이미 저장된 행은 아니다. 해결책(예: source 에 요약 필드도 포함 / 오염 기사를 입력에서 제외)은 이번 범위 밖이라 손대지 않았다. *(오케스트레이터: source 에 모델 입력 전체를 넣는 쪽으로 반영. 과거 오염 행은 T6 치환으로 정리)*
- 3회 호출 후 실패하면 리포트가 그날 아예 없다(저장 안 함). 지시 그대로이며, 크론이 다음 날 재시도하지 않으므로 운영 알림/수동 재실행 절차가 필요하다.

## T5 일괄 저장

### 바꾼 파일
- `src/services/database.ts` — `saveNewsArticlesBatch` 가 `getExistingLinks` 조회 + `$transaction([...upsert])` 대신 `db.article.createMany({ data, skipDuplicates: true })` 한 번을 부르고 `count` 를 신규 저장 수로 돌려준다. 중복 수 로그는 `articles.length - count`. `try/catch` 와 개별 저장 폴백(`saveNewsArticles`)은 그대로. `getExistingLinks` 는 `news-analyzer.ts` 의 Stage 0 이 쓰므로 export 유지.
- `tests/database.test.ts` — `database` import 와 `mock` 추가, `describe("saveNewsArticlesBatch")` 4개 추가(기존 테스트 변경 없음).

### 판단한 것과 이유
1. **`spyOn(database, "getPrisma")` 가 모듈 내부 호출도 가로챈다(실측).** 처음에는 같은 모듈 안의 `getPrisma()` 호출은 못 가로챈다고 짐작해서 싱글턴 클라이언트의 메서드를 spyOn 하는 방식으로 썼다가, (a) Prisma 클라이언트 모델 메서드는 프록시라 `spyOn(db.article, "createMany")` 가 실제로 안 걸리는 것(RED 에서 가짜 `findMany` 인데도 WebSocket 연결 오류)과 (b) 임시 테스트로 `spyOn(database, "getPrisma")` 가 `saveNewsArticlesBatch` 안에서 3번 호출 가로채짐(`spyCalls: 3`)을 확인했다. 그래서 지시대로 `getPrisma` 를 목으로 바꾸고 가짜 db 객체(`article.createMany/findMany/findUnique/create`, `$transaction`)를 돌려준다. 임시 테스트 파일은 지웠다.
2. 가짜 `findMany` 가 불리지 않았는지도 확인한다(저장 전 `getExistingLinks` 조회가 사라졌음을 고정).
3. 폴백 테스트는 `saveNewsArticles` 를 직접 spy 하지 않고(모듈 내부 호출) `findUnique`/`create` 호출 3번씩으로 확인한다. `$transaction` 이 폴백 경로에서도 안 불리는 것까지 본다.
4. `skipDuplicates` 는 PostgreSQL 에서 `ON CONFLICT DO NOTHING` 이라 `update: {}` upsert 와 의미가 같다. 같은 배치 안의 중복 링크도 하나만 들어간다. 이때 `count` 는 실제 삽입 행 수이므로 반환값이 `articles.length` 보다 작을 수 있다 — 호출부(`jobs/collect-news.ts`)가 이 값을 "저장 수"로만 쓰는지는 확인하지 않았다.

### 의심스러운 것
- **실제 DB 에서 한 번도 돌려 보지 않았다**(더미 환경). Neon 어댑터 + `createMany` + JSON 컬럼(`Prisma.DbNull`) 조합이 운영에서 5초 한도 안에 끝나는지는 H4 dry-run 이 아니라 실제 저장 실행에서만 확인된다. 기사 20개 한 번의 INSERT 라 한도 안일 가능성이 높지만 측정은 못 했다.
- 한 행이라도 제약 위반(unique 외)이면 배치 전체가 실패하고 폴백으로 개별 저장한다(이전 `$transaction` 도 전체 롤백이라 동일).
